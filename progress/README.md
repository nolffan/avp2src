# progress/ -- how much of the build is byte-identical to the retail game

The legacy build must compile to exactly the machine code of the retail
game. The retail game is *Primal Hunt* 1.0.2.2, which is the last release,
and the parts of *Aliens versus Predator 2* 1.0.9.6 that Primal Hunt does
not replace. This directory holds:

- the record of the progress to this goal,
- the description of what is scored,
- the evidence that the scoring needs.

The table below is made from this record.

```sh
make                       # build (the scoring reads the output)
make progress              # score the build; fail on a regression
make progress-update       # record the score here, and write the table below again
```

The file `progress/identical.txt` records each function in that table.
`make progress` scores the current build again against the retail
binaries. It fails if one of these functions does not match any more. The
sections below tell how the scoring works and what it does not include.
`COMPILERS.md` tells which compiler built each binary, and gives the
evidence.

## What is scored

`targets.py` lists all the shipped binaries. For each binary, it gives the
location of the binary's own code and the location of our build of it.
`ext/tools/progress.py` and `ext/tools/ratchet.py` do not know a binary by
name. To add a new binary (for example an engine binary, when its source
exists), add it to `targets.py`, with the evidence for its ranges.

| Binary | Compared against | Our side |
|---|---|---|
| `lithtech.exe`, `server.dll`, `d3d.ren`, `cdaudio.dll`, `Launch.dll`, `PrimalHunt.exe`, `AVP2XServ.exe`, `PHCShell.dll`, `PHObject.lto` | The retail binaries of Primal Hunt. `build/reference.sh` extracts them from the installed game into `out/reference/`. The game DLLs come from its `AVP2DLL.REZ`, with names that are different from the AvP2 names (`build/retail.py`). | The image that `make` built (`src/.../built/Final/...`). Also each object and library of ours that its link read, from the response file of the link beside it (`<image>.rsp`). A binary that has no build yet scores as all unwritten, and is counted. |
| `AVP2.exe`, `AVP2Serv.exe`, `CShell.dll`, `Object.lto` | The AvP2 1.0.9.6 binaries, in the same way. The game DLLs come from `AVP2DLL.REZ`, which the patch replaced (`build/retail_avp2.py`). | The same. |
| `ltmsg.dll`, `AVP2XUp.dll`, `PHCRes.dll`, `PHSRes.dll`; `AVP2Up.dll`, `CRes.dll`, `SRes.dll` | The same. | Resource by resource. Their only code is the DLL entry of the C runtime and an empty `DllMain`. They are listed after the code, and they are not in the total. |

The retail images have no symbols. Thus the scorer finds their functions
from the code itself (call targets, vtables, callbacks, exports, ...).
Then it searches the image for each of our compiled functions. A function
is **identical** when our bytes are equal to the retail bytes at all
locations, except where the linker writes an address. These locations are
the relocations, which an unlinked object leaves blank.

Our libraries (ButeMgr, StdLith, CryptMgr, ...) are built from source. They
are scored in the binaries that link them. The source release also has
them as prebuilt libraries (`lithshared/libs/`, cl 8966). nolfsrc scores
the prebuilt NOLF libraries alone. A score of these prebuilt libraries
alone, in the same way, is for later.

Each retail function gets one status (`out/progress/functions.csv`):

| Status | Meaning |
|---|---|
| `identical` | Our code is the retail code, but for the relocations. |
| `near` | We have the function, but the bytes are different. |
| `small` | We have the function, but it is almost all relocations (global initializers). Thus there is nothing to compare. It is reconstructed, but not verified. |
| `attempted` | There is no match, but `src/` or the CSVs here cite the address. |
| `todo` | Nothing of ours corresponds to it yet. |
| `crt` | It is outside the binary's own code (`app` in `targets.py`): the static C runtime and MFC, the import thunks, and the `.text$x` exception funclets. It is listed, but not counted. |
| `middleware` | Third-party code that is linked among the binary's own code. It is listed, but not counted (see below). |
| `encrypted` | Code that a retail image keeps encrypted on the disc. It is listed, but not counted. AvP2 has none (see below). |

Four more statuses are for functions of OURS, not for shipped functions.
Thus none of them is counted in the denominator:

| Status | Meaning |
|---|---|
| `unplaced` | It is written, and our own link puts it in our image, but no shipped function is placed for it. |
| `unreferenced` | Like `unplaced`, but nothing that the `/OPT:REF` of the retail link keeps refers to it. Thus the retail link would have discarded it. (Our scoreboard links use `/OPT:NOREF`: build/build.mk.) It is a template member, or an inline or compiler-generated helper, that only an explicit instantiation or dead code of ours emits. An out-of-line definition never has this status, because its caller can be retail code that is not written yet. |
| `unlinked` | It is compiled, but our own link also leaves it out. It is a library member that this binary does not pull. |
| `driver` | Only a scoring driver emits it, and that driver ships nowhere. There are none here. |

The bars in the README show the identical bytes divided by all the counted
bytes. The total is the code of the full game, with the engine.

### What is not counted

* **The C runtime.** Each binary links it statically, as the NOLF binaries
  do (`libcmt.lib`). The launcher and the dedicated server also link MFC's
  `nafxcw.lib`. `Launch.dll` is a Debug build and links `libcmtd.lib`. The
  runtime comes after the binary's own code. `targets.py` gives the
  boundary of each binary and how it was found. (`ext/tools/libscan.py`
  places the functions of a library in a retail image. When a binary links
  here, our `.map` gives the library of each of our functions.) If the
  linker put code of the binary's own after the runtime, that code is a
  second `app` range.
* **Third-party libraries** (`middleware`). nolfsrc leaves out the GameSpy
  SDK in the NOLF game DLLs, and this project does the same. These
  libraries are the GameSpy SDK and the WON API (`lithshared/gamespy`,
  `lithshared/wonapi`). Their strings are in the game DLLs and the engine.
  Their blocks are not placed yet (`targets.py`). STLport and MS STL
  templates that are instantiated in the game's own objects are different.
  They are compiled from headers here, like all inline functions, and they
  are counted.
* **Copy protection.** The Primal Hunt engine has no copy protection, and
  the AvP2 1.0.9.6 engine had none. No code is encrypted. The launchers,
  `AVP2.exe` and `PrimalHunt.exe`, each have two sections that a
  protection wrapper added: `.cms_t`, which holds its entry point, and
  `.cms_d`. These sections are not encrypted. They are not counted,
  because they are outside the `app` range of `.text`. This project does
  not remove or bypass the protection.

## Coverage: unwritten and unplaced

In addition to identity, the scoreboard measures coverage. The README
shows the coverage for each binary:

* **Unwritten**: shipped functions that have nothing of ours placed at
  them (`todo` + `attempted`).
* **Unplaced**: functions of ours in our own image for which no shipped
  function is placed.

When the two counts are zero, the build is complete. Then each shipped
function has a written, placed counterpart, near or identical, and no
function of ours is extra. After that, to get identity, make the near
functions identical.

The scorer first places a function by its bytes (identical, or `small` by
shape). Then it places a function by similarity (`near`: the same length
within 15%, and most of the unmasked bytes agree). These two methods miss
some functions. An example is a function that is written correctly but
compiled with other registers, another block order, or a different member
offset. Without more help, the scorer counts such a function two times:
once as an unwritten shipped function and once as an unplaced function of
ours. Thus the scorer also joins the two sides. A function that it joins
in this way is `near`:

1. **By name**: A function that has the name of the shipped address it
   reconstructs (`sub_<addr>`) is placed at that address. This is true
   also when it compiled very differently.
2. **By object**: The linker puts the functions of an object together.
   Thus a shipped function that has nothing placed at it, and whose
   nearest placed neighbours are functions of object X, is a function of
   X. The scorer matches the unplaced functions of X to these functions by
   size, closest first (within a factor of two).
3. **By link order**: The remaining functions between two neighbouring
   functions that are placed in both images are aligned in order by size.
   (Our `.map` gives our addresses.)

An inline function from a header is compiled into each object that
includes it. The linker keeps one copy. Thus, when the scorer places one
copy, it places all of them. Some functions are too short to tell apart
(`mov eax,8 / ret`, an initializer thunk of one `jmp`). The scorer counts
these by shape. For each exact shape, the number of our unplaced functions
is only the number by which our image has more of them than the shipped
image. Sometimes the enumeration misses a function start, for example a
function that only a thunk reaches. (The incremental link of the launcher
puts a thunk in front of each call.) The scorer finds such a start where
one of our functions matches inside another row, and the row ends there.

`make progress` fails if one of the two counts increases.
`make progress COVERED=1` fails if the two counts are not zero for all
binaries. `ext/tools/progress.py --unplaced=<target>` and
`--todo=<target>` (and also `--attempted`, `--near` and `--small`) list
the functions. `--nears` lists the near matches, closest first.

This is the measure for each function. A full binary is byte-perfect only
when all its functions are identical *and* it links in the same order,
with the same data and headers. `ext/tools/bindiff.py` makes this
comparison of the full file.

## The test

The scoring includes only the release (legacy) build. The debug and modern
builds are built in other locations (`build/variant.sh`), and the scoring
never reads them.

`progress/identical.txt` lists each function that is verified identical.
`progress/summary.json` gives the totals of these functions.
`make progress` (`build/progress.sh check`) scores the current build
again. It fails if one of these conditions occurs:

* A function in `identical.txt` is not identical any more.
* The identical byte count of a target decreased.
* The unwritten or unplaced count of a target increased.
* The table in `README.md` is not the table that `summary.json` renders.
* The data check finds a difference that `data-known.txt` does not list
  with its reason. The data check (`ext/tools/datacheck.py`) compares the
  text in the data of our images (strings, import and export names) with
  the text in the retail images.
* `ext/tools/fpconst.py` finds a float or double that is different from
  retail. This is a constant that one of our placed functions loads,
  through an address that the byte match masks. It is different from the
  constant that retail loads there. A masked match is identical only up to
  the constants that it reads.
* `ext/tools/vtabcheck.py --targets` finds a contradiction that
  `progress/vtab-known.txt` does not list. A contradiction is a vtable
  slot of ours, or a call or global that one of our functions reaches,
  that is different from the retail one. The tool makes a decision only
  where the evidence is clear: the body of the function fits exactly one
  retail address, and the same code under another name agrees. It counts
  all other cases as unverified, not as passed.

Each run also writes `out/progress/evidence.json` (`ext/tools/evidence.py`).
This file has:

* the source and submodule revisions,
* the hash of each retail image,
* the configuration and exclusion files,
* our images, maps and link commands,
* the toolchain trees that the build used. The run checks their digests
  against the pins in `ext/toolchains/fetch.sh`. A mismatch makes the run
  fail.

`make progress-update` keeps a copy as `progress/evidence.json`.

Before the scorer scores anything, it checks the retail images in the
cache `out/reference/` against `progress/reference.sha256`. If they are
different, it extracts them again from the installed game. Thus the scorer
always scores the retail release, not other contents of the cache.

Newly identical functions pass, and the test tells you to record them.
`make progress-update` writes `identical.txt`, `summary.json` and the
README table again. After that, the test holds the build to the
improvement. `make progress-update` refuses a run that lost a recorded
function, unless you give `ACCEPT_LOSSES=1`. Use this when a change
correctly loses a function, for example a function that matched by
coincidence.

`make progress COMPLETE=1` also fails if a function of a target is not
identical, or if a function is unwritten or unplaced (`COVERED=1` alone
does this second check). This is the finish line for the code. It is not
the identity of the full image: `ext/tools/buildcmp.py` against the retail
image checks that. If the full image of a target is already the retail
image (but for the time stamps of the link), the scorer scores all its
functions identical. This is true also when the masked match can prove
little of it.

The scoring compiles nothing. It reads what the last `make` left in the
tree. After you change the source, do `make`. Then do `make progress`. The
scoring needs only Python 3. Thus `build/progress.sh check` works directly
inside `make shell`, or on a host with Python.

## Files

| File | What |
|---|---|
| `targets.py` | The binaries that are scored. For each binary: its retail image, our build, its own code (`app`), and what is left out (`middleware`, `encrypted`), with the evidence. |
| `identical.txt` | Each function verified identical (`target<TAB>function`). This is the baseline that the test holds the build to. `make progress-update` writes it. |
| `summary.json` | The counts and bytes for each target from the recorded run. The README table is rendered from it. |
| `reference.sha256` | The retail images that `out/reference/` must hold for the scoring. |
| `vtab-known.txt` | The known vtable and wiring differences that `ext/tools/vtabcheck.py` finds, each with its reason. |
| `evidence.json` | The data that the recorded run used (`ext/tools/evidence.py`). |
| `data-known.txt` | The known text differences from the retail images, each under its reason (`ext/tools/datacheck.py`). |
| `COMPILERS.md` | The compiler and flags that built each retail binary, and the evidence. |
| `<stem>-screen-exclude.csv` | (None yet.) For each image, the enumerated addresses that a person examined. A reason that starts with `NOT A FUNCTION` or `NOT GAME CODE` removes the row from the count. All other reasons mark the address `attempted` in an image whose addresses `src/` cites. |
| `extent-splits.csv` | (None yet.) Function starts that the enumeration misses, with the evidence. |

The CSVs change what is counted. Thus a change to them is a change to the
denominator. Give the evidence in the reason.

This directory does not keep the function and vtable tables for each image
(`out/reference/<stem>-functions.csv`, `-vtables.csv`). `build/reference.sh`
makes them from the retail images.

Each run writes these files in `out/progress/`: `functions.csv` (each
retail function and its status) and `summary.json`.
