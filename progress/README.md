# progress/ -- how much of the build is byte-identical to the retail game

The goal of the legacy build is to compile to exactly the machine code of
the retail game: *Primal Hunt* 1.0.2.2, the last release, and the parts of
*Aliens versus Predator 2* 1.0.9.6 it does not replace. This directory
holds the record of how far that has got, the description of what is
scored, and the evidence the scoring needs. The table below is generated
from it.

```sh
make                       # build (the scoring reads its output)
make progress              # score it; fails on any regression
make progress-update       # record the score here, and rewrite the table below
```

## Progress

(Primal Hunt 1.0.2.2; AvP2 1.0.9.6 for AvP2's own game, launcher and
dedicated server). A function counts when our compiled code is identical to the
retail function, with only the addresses the linker fills in left out of
the comparison; the bars measure the share of each binary's code, by size,
those functions make up.

Every function in that table is recorded in `progress/identical.txt`, and
`make progress` re-scores the current build against the retail binaries and
fails if any of them stops matching. The sections below describe how the
scoring works and what it leaves out. Which compiler built each binary, and
the evidence, is `COMPILERS.md`.

## What is scored

`targets.py` lists every shipped binary, with where its own code is and
where our build of it is. `ext/tools/progress.py` and `ext/tools/ratchet.py` know
no binary by name; a new one (an engine binary, once its source exists) is
added there, with the evidence for its ranges.

| Binary | Compared against | Our side |
|---|---|---|
| `lithtech.exe`, `server.dll`, `d3d.ren`, `cdaudio.dll`, `Launch.dll`, `PrimalHunt.exe`, `AVP2XServ.exe`, `PHCShell.dll`, `PHObject.lto` | Primal Hunt's retail binaries, extracted from the installed game into `out/reference/` (`build/reference.sh`; the game DLLs from its `AVP2DLL.REZ`, under names apart from AvP2's: `build/retail.py`) | the image `make` built (`src/.../built/Final/...`) and every object and library of ours its link read, from the link's response file beside it (`<image>.rsp`). A binary with no build yet scores as all unwritten, and is counted |
| `AVP2.exe`, `AVP2Serv.exe`, `CShell.dll`, `Object.lto` | AvP2 1.0.9.6's, the same way (the game DLLs from `AVP2DLL.REZ`, which the patch replaced: `build/retail_avp2.py`) | the same |
| `ltmsg.dll`, `AVP2XUp.dll`, `PHCRes.dll`, `PHSRes.dll`; `AVP2Up.dll`, `CRes.dll`, `SRes.dll` | the same | resource by resource: their only code is the C runtime's DLL entry and an empty `DllMain`. Listed after the code, not in the total |

The retail images have no symbols, so their functions are enumerated from
the code itself (call targets, vtables, callbacks, exports, ...), and each
of our compiled functions is searched for in the image. A function is
**identical** when our bytes equal the retail bytes everywhere except where
the linker writes an address (relocations, which an unlinked object leaves
blank). Libraries of ours (ButeMgr, StdLith, CryptMgr, ...) are built from
source and scored inside the binaries that link them. The source release
ships them prebuilt too (`lithshared/libs/`, cl 8966); scoring those on
their own, as nolfsrc scores NOLF's prebuilt libraries, is for later.

Each retail function gets one status (`out/progress/functions.csv`):

| Status | Meaning |
|---|---|
| `identical` | our code is the retail code, relocations aside |
| `near` | we have the function, but the bytes differ |
| `small` | we have it, but it is almost all relocations (global initializers), so there is nothing to compare: reconstructed, not verified |
| `attempted` | no match, but the address is cited in `src/` or recorded in the CSVs here |
| `todo` | nothing of ours corresponds to it yet |
| `crt` | outside the binary's own code (`app` in `targets.py`): the static C runtime and MFC, import thunks, the `.text$x` exception funclets: listed, not counted |
| `middleware` | third-party code linked among the binary's own: listed, not counted (below) |
| `encrypted` | code a retail image keeps encrypted on disc: listed, not counted (none in AvP2: below) |

Four more statuses are for functions of OURS, not shipped ones, so none of
them is counted in the denominator:

| Status | Meaning |
|---|---|
| `unplaced` | written, and our own link puts it in our image, but no shipped function is placed for it |
| `unreferenced` | as `unplaced`, but nothing the retail link's `/OPT:REF` keeps references it, so it would have discarded it (our scoreboard links are `/OPT:NOREF`: build/build.mk): a template member, inline or compiler-generated helper only an explicit instantiation or dead code of ours emits. An out-of-line definition is never this (its caller may be retail code not yet written) |
| `unlinked` | compiled, but our own link leaves it out too: a library member this binary does not pull |
| `driver` | emitted only by a scoring driver that ships nowhere (none here) |

The README's bars are identical bytes over all counted bytes, and the total
is the whole game's code, the engine's included.

### What is not counted

* **The C runtime.** Every binary links it statically, as NOLF's do
  (`libcmt.lib`; the launcher and the dedicated server also MFC's
  `nafxcw.lib`; `Launch.dll`, a Debug build, `libcmtd.lib`), after the
  binary's own code. `targets.py` gives each binary's boundary and how it
  was found (`ext/tools/libscan.py` places a library's functions in a retail
  image; once a binary links here, our `.map` names the library of each of
  our functions). Code of the binary's own that the linker put after the
  runtime is a second `app` range.
* **Third-party libraries** (`middleware`), as nolfsrc leaves out the
  GameSpy SDK in NOLF's game DLLs: the GameSpy SDK and WON's API
  (`lithshared/gamespy`, `lithshared/wonapi`; their strings are in the game
  DLLs and the engine). Their blocks are to be placed (`targets.py`).
  STLport and MS STL templates instantiated in the game's own objects are
  compiled from headers here, like any inline function, and are counted.
* **Copy protection.** Primal Hunt's engine has none (nor had AvP2
  1.0.9.6's), and no code is encrypted. The launchers, `AVP2.exe` and
  `PrimalHunt.exe`, each carry two sections a protection wrapper added (`.cms_t`, which holds its entry point, and `.cms_d`); they
  are not encrypted, and not counted, being outside `.text`'s `app`. The
  protection is not removed or bypassed.

## Coverage: unwritten and unplaced

Next to identity, the scoreboard measures coverage, and the README shows it
per binary:

* **Unwritten**: shipped functions with nothing of ours placed at them
  (`todo` + `attempted`).
* **Unplaced**: functions of ours in our own image that no shipped function
  is placed for.

Both at zero means the build is complete: every shipped function has a
written, placed counterpart, near or identical, and nothing of ours is left
over. Identity is then a matter of converging the near ones.

A function is placed first by its bytes (identical, or `small` by shape), then
by similarity (`near`: same length within 15% and most unmasked bytes
agreeing). What both miss -- a function written right but compiled with
other registers, another block order, a different member offset -- would
otherwise be counted twice, once as an unwritten shipped function and once
as an unplaced one of ours. So the scorer also joins the two sides, and a
function joined this way is `near`:

1. **By name**: a function named for the shipped address it reconstructs
   (`sub_<addr>`) is placed there, however differently it compiled.
2. **By object**: the linker lays an object's functions out together, so a
   shipped function nothing is placed at, whose nearest placed neighbours are
   object X's, is one of X's; X's unplaced functions are matched to those by
   size, closest first (within a factor of two).
3. **By link order**: what is left, between two neighbouring functions placed
   in both images (our `.map` gives our addresses), is aligned in order by
   size.

An inline function from a header is compiled into every object that
includes it; the linker keeps one copy, so placing one places them all.
Functions too short to tell apart (`mov eax,8 / ret`, a one-`jmp`
initializer thunk) are counted by shape: of each exact shape, ours are
unplaced only by as many as our image has more of than the shipped one. A
start the enumeration missed (a function reached only through a thunk,
which the launcher's incremental link puts in front of every call) is found
where one of our functions matches inside another row, and the row ends
there.

`make progress` fails if either count goes up; `make progress COVERED=1`
fails unless both are zero everywhere. `ext/tools/progress.py --unplaced=<target>`
and `--todo=<target>` (and `--attempted`, `--near`, `--small`) list them,
and `--nears` lists the near matches closest first.

This is the per-function measure. A whole binary is byte-perfect only once
every function is identical *and* it links in the same order, with the same
data and headers; `ext/tools/bindiff.py` makes that whole-file comparison.

## The test

Only the release (legacy) build is scored. The debug and modern builds are
built elsewhere (`build/variant.sh`), and the scoring never reads them.

`progress/identical.txt` lists every function verified identical, and
`progress/summary.json` the figures they add up to. `make progress`
(`build/progress.sh check`) re-scores the current build and fails if:

* a function listed in `identical.txt` is no longer identical,
* a target's identical byte count went down,
* its unwritten or unplaced count went up,
* `README.md`'s table is not the one `summary.json` renders,
* the data check (`ext/tools/datacheck.py`: the text in our images' data --
  strings, import and export names -- against the retail images') finds a
  difference `data-known.txt` does not list with its reason,
* `ext/tools/fpconst.py` finds a float or double that one of our placed
  functions loads (through an address the byte match masks) differing
  from the one retail loads there: a masked match is identical only up to
  the constants it reads, or
* `ext/tools/vtabcheck.py --targets` finds a contradiction
  `progress/vtab-known.txt` does not list: a vtable slot of ours, or a call
  or global one of our functions reaches, that is another one than retail's
  -- judged only where the evidence is unambiguous (the function's body fits
  exactly one retail address; same code under another name agrees), and
  everything else counted as unverified, not passed.

Each run also writes `out/progress/evidence.json` (`ext/tools/evidence.py`):
the source and submodule revisions, every retail image's hash, the
configuration and exclusion files, our images, maps and link commands, and
the toolchain trees the build used with their digests checked against
`ext/toolchains/fetch.sh`'s pins (a mismatch fails the run).
`make progress-update` keeps a copy as `progress/evidence.json`.

Before anything is scored, the retail images cached in `out/reference/`
are checked against `progress/reference.sha256` (and extracted again from
the installed game if they differ): what is scored is always the retail
release, not whatever the cache holds.

Newly identical functions pass, with a reminder to record them:
`make progress-update` rewrites `identical.txt`, `summary.json` and the
README table, so the improvement is locked in from then on. It refuses a
run that lost a recorded function unless `ACCEPT_LOSSES=1` is given (when a
change rightly gives one up -- say, a function was matched by coincidence).

`make progress COMPLETE=1` also fails unless every function of every target
is identical, and nothing is unwritten or unplaced (`COVERED=1` alone): the
finish line for the code. It is not whole-image identity, which
`ext/tools/buildcmp.py` against the retail image is. A target whose whole
image already is retail's (but for the link's time stamps) scores every
function identical, however little of it the masked match could prove.

The scoring compiles nothing; it reads what the last `make` left in the
tree. Run `make` after changing the source, then `make progress`. It needs
Python 3 only, so inside `make shell` (or on a host with Python)
`build/progress.sh check` works directly.

## Files

| File | What |
|---|---|
| `targets.py` | the binaries scored: for each, its retail image, our build, its own code (`app`), and what is left out (`middleware`, `encrypted`), with the evidence |
| `identical.txt` | every function verified identical (`target<TAB>function`): the baseline the test holds the build to. Written by `make progress-update` |
| `summary.json` | per-target counts and bytes of the recorded run; the README table is rendered from it |
| `reference.sha256` | the retail images `out/reference/` must hold to be scored |
| `vtab-known.txt` | the vtable and wiring differences `ext/tools/vtabcheck.py` finds that are known, each with its reason |
| `evidence.json` | what the recorded run rested on (`ext/tools/evidence.py`) |
| `data-known.txt` | the text differences from the retail images that are known, each under its reason (`ext/tools/datacheck.py`) |
| `COMPILERS.md` | which compiler and flags built each retail binary, and the evidence |
| `<stem>-screen-exclude.csv` | (none yet) per image, enumerated addresses examined by hand. A reason that starts `NOT A FUNCTION` or `NOT GAME CODE` removes the row from the count; any other reason marks the address `attempted` in an image whose addresses `src/` cites |
| `extent-splits.csv` | (none yet) function starts the enumeration misses, with the evidence |

The CSVs change what is counted, so a change to them is a change to the
denominator: give the evidence in the reason.

The per-image function and vtable tables (`out/reference/<stem>-functions.csv`,
`-vtables.csv`) are not kept here: `build/reference.sh` derives them from
the retail images.

Per run, in `out/progress/`: `functions.csv` (every retail function and its
status) and `summary.json`.
